**How to reach the theme's custom JS/CSS editor (this is NOT obvious, took a while to find):**
Dashboard → المتجر الإلكتروني → الثيمات (`/ar-sa/stores/3168409/channels/online-store/themes`) → on the current active theme card ("نمو") click the "⋮" button → dialog "الإجراءات" opens with 3 options: معاينة / تعديل التصميم من خلال CSS / تعديل JS. This is DIFFERENT from the theme-editor page's own "⋮" menu (which only has تصدير/استيراد/معاينة — not the code editor).
**How to apply:** don't confuse the two "⋮" menus; the code editor only lives on the Themes list page, not inside the visual theme-editor.

**Editing the JS box reliably (it's a CodeMirror 6 contenteditable, `.cm-content`):**
Typing character-by-character via computer-tool `type` risks CodeMirror's auto-bracket-closing mangling the content. `navigator.clipboard.writeText` + Ctrl+V HUNG the page (45s CDP timeout, likely a stuck permission prompt) — avoid clipboard entirely. The reliable method: via `javascript_tool`, `el = document.querySelector('.cm-content')`, focus it, build a `Range`/`Selection` over `selectNodeContents(el)`, then `document.execCommand('insertText', false, fullNewContent)` — replaces (or appends, if the range is collapsed to the end) cleanly in one shot. Always verify by screenshot (check final line number looks sane) before clicking "حفظ".
**How to apply:** reuse this exact method for any future custom-JS edits on this store.

**Delivery mechanism:** saved JS compiles to an external, cache-busted asset: `https://static.zid.store/static/19739da0-0db0-4339-828b-796e37f40b74/custom-scripts.js?v=<timestamp>`, loaded via `<script src=... defer>` on every storefront page. The version querystring only changes on a real successful rebuild.

**SKU search-spacing fix — two independent parts, both live and verified working as of 2026-09-08:**

Background: Audi/VW/Porsche (VAG-group) OEM part numbers are stored in Zid with spaces in the fixed format "XXX XXX XXXX" (e.g. "8K0 505 323H"). Customers type them without spaces (as printed on the physical part), and Zid's search does exact-substring matching, so it returns zero results even though the product exists. BMW's SKU convention (C/T + 9 digits, no spaces) is untouched by any of this — it was never broken.

1. **Results-page fallback** (`/products?q=...`): only acts when the native search already returned zero results. If the query (spaces/dashes/slashes stripped) matches a COMPLETE bare VAG part number (`^[0-9][A-Za-z0-9]{8,10}$`, must also contain a letter — i.e. 9-11 chars total), reinsert standard spacing and redirect once via `window.location.href`. A `sessionStorage` guard (`skuFixTried:<compact>`) prevents redirect loops.
   **Gotcha:** re-testing the exact same query in the SAME browser tab after it already redirected once will NOT redirect again (guard already set) — looks like "broken" during testing but isn't. Clear via `sessionStorage.removeItem('skuFixTried:<COMPACT>')` or just use a fresh tab to retest.

2. **Live "as-you-type" search dropdown fix:** the header search's live suggestions do NOT navigate to the results page — they call `/api/v1/products?q=...` (JSON API, shape `{results:[], count, page, page_size, filters, next, previous, pages_count}`) directly via `window.fetch` on every keystroke, completely bypassing fix #1. Patches `window.fetch`: intercepts calls to this endpoint, and if `count===0` and the query (spaces stripped) matches a LOOSER partial pattern (`^[0-9][A-Za-z0-9]{0,13}$`, no letter required yet since it may not be typed yet), progressively reformats with spacing (≤3 chars: none yet; 4-6: one space after char 3; 7+: two spaces after char 3 and char 6) and silently retries, handing the app whichever response actually has results.
   **Key empirical finding that made this possible:** Zid's `/api/v1/products` search does real PREFIX/substring matching once spacing is correct — confirmed "8K0" alone → 81 matches, "8K0 505" → 2, "8K0 505 3" → 2 (all against the same product). The search engine was never the limitation — only the missing spaces were. This means the live dropdown now updates in real time as a customer types a partial part number, not just on a complete one.

Both parts are purely positional/algorithmic — no product database is embedded in the script, no per-product data needed, so they keep working automatically as new VAG products are added without any maintenance.

**Testing gotcha (browser tools):** the header search overlay sometimes needs the search-icon click sent TWICE in a row before it visually opens (first click occasionally no-ops) — always screenshot after clicking to confirm the overlay is actually open before typing, rather than assuming.

**Also discovered during this fix: the JS box is a CodeMirror 6 VIRTUALIZED editor — `.cm-content.textContent` only returns whatever's currently rendered in the viewport, NOT the full saved document, for long content.** Reading back "the whole box" via textContent silently truncates (returned only ~1742 of what should have been several KB, cutting off mid-function, with no error/warning). This is NOT the same corruption bug as before (the deployed/live script was fine — verified via an immediate live redirect test — only the *read-back-for-inspection* was truncated). **How to apply:** never trust `.cm-content.textContent` as a complete read for a non-trivial script in this editor. To make any future edit, either (a) reconstruct the full file fresh from memory/known-good source (safe if you have the exact prior content recorded, as we did here with the Clarity/GTM IDs), or (b) if you must preserve unknown existing content, read it in small sequential slices (e.g. `textContent.slice(0,200)`, `.slice(200,400)`, ...) and concatenate — single large reads cannot be trusted complete.

**New matching approach (v4), same two-part structure as before:**
1. **`candidateSpacings(compact)`**: instead of one fixed spacing guess, generates candidates for inserting the first space at offset 0, 1, or 2 (covers a fragment starting anywhere within a 3-char segment) plus the raw no-space form. This fixes both original bugs at once:
   - **Case sensitivity**: compact form is always `.toUpperCase()`'d before comparison — Zid's search is case-sensitive, stored letters are uppercase (e.g. "...081 B"), so a lowercase "081b" query needs uppercasing to have any chance of matching.
   - **Fixed-offset assumption**: a fragment like "7081" bridging mid-segment (last digit of "807" + all of "081") needs the space inserted after char 1 ("7 081"), not the old fixed after-char-3 rule ("708 1") — confirmed via live API testing that "7 081" → 7 real matches, "708 1" → 0.
2. **Fix 1 (results-page fallback) redesigned to check the API directly** (`fetchCount(q)` against `/api/v1/products` for the literal typed query) instead of scraping the DOM for a "no results" message — the old DOM-text approach (`لا توجد منتجات`) doesn't reliably appear on the `/products?q=...` results page (that page has a persistent hidden loading-skeleton text fragment that made text-scraping unreliable/misleading during testing). Also removed a bad `compact !== q` gate that accidentally skipped the whole fix whenever the query was *already* in compact form with nothing to strip (e.g. "7081" itself) — exactly the most common real case. Caught via live testing, not by simulation.
3. **Fix 2 (live dropdown)** unchanged in structure, just uses the new multi-offset `candidateSpacings` + uppercase.

**Final v6 design, two different mechanisms per surface (user chose "did you mean banner" over "dropdown-only" when asked):**
1. **Live dropdown** (`/api/v1/products?q=...`, IS client-fetched): true merge. Fetches native first; if native count ≤ 5, also fetches every candidate spacing in parallel and merges all unique products (dedup by `id`) into one combined response the dropdown renders. If native count > 5, skips the extra fetches entirely (perf: cut a broad query like "8K0" from ~975ms to ~268ms by not bothering to merge when there's already plenty of results).
2. **Results page** (server-rendered, can't merge): unchanged zero-result redirect behavior from v4, PLUS a new **injected "did you mean: [product name]" banner** (id `sku-fix-banner`, styled inline, inserted at the top of `<main>`) whenever native found something (so no redirect) but a differently-spaced candidate finds genuinely DIFFERENT products (checked via id comparison, not just count) — links to the alternate query, doesn't touch/hide the native result.

"081b" live dropdown → merged response, count 2, both products. Broad "8K0" → 268ms (no unnecessary merge). "7081" (zero-native case) → still redirects correctly to "7 081". **Year-compatibility category filter — BUILT, DEPLOYED, AND VERIFIED LIVE 2026-09-10.** Real client-side workaround for the "no storefront filter for vehicle year" gap (attribute/option-based filtering rejected as a false path - see [[project_laser_auto_parts]] for the full investigation: Zid Options fork one product into N fake variants per value checked, and category pages aren't even customizable in the نمو theme editor at all, so no attribute-filter block exists to add there either).
**How it works:** on any `/categories/<id>/...` page, fetches the full product list from the public storefront API using `categories=<id>` (plural - confirmed the only param that actually filters; `category`/`category_id`/`category_ids` are all silently ignored, same platform quirk as the dashboard Products API), paginating via `page_size=100` + `next` if needed. **Never fabricates:** if a category has zero year-tagged products, the dropdown simply doesn't render - verified live on the BMW root category (436 products, 0 years found, no dropdown). Coverage is inherently partial: only the ~568 Audi products that had a real "Compatible Years" bullet in their description got tagged, so only categories built from those show this control; BMW/Porsche/VW categories show nothing until/unless that same title-tagging pass is ever done for them.

**Bug found and fixed 2026-09-11: year-filter's own `buildCardHtml` was rendering broken images for products that DO have a photo.** Owner reported (with screenshot) that normal category browsing shows images fine, but filtering by year showed some products with broken/unavailable image icons. Root cause: `buildCardHtml` read `p.images[0].thumbnail` directly, but the real `/api/v1/products` shape nests it one level deeper — `p.images[0].image.thumbnail` (the `image` field is an object with `{full_size,large,medium,small,thumbnail}`, not a URL itself). So for any product with an uploaded photo, the code stuffed the whole `image` object into `<img src>` (stringifying to "[object Object]"), while products with zero images correctly fell through to the gray-placeholder fallback (which is why the bug looked inconsistent — some cards fine, some broken, seemingly at random, but it actually correlated exactly with "does this product have a photo or not").
**Fix:** `var imgObj = p.images && p.images[0] && p.images[0].image; var img = (imgObj && (imgObj.thumbnail || imgObj.medium || imgObj.small || imgObj.full_size)) || p.main_image || null;` — deployed via the CodeMirror editor's own built-in search/replace panel (opened with Ctrl+F inside the `.cm-content` editor; it has separate Find/Replace fields plus next/previous/all and replace/replace-all buttons) rather than a full-content reconstruction, since **`get_page_text` on the live `custom-scripts.js` truncates large files silently** (got cut off ~1000 chars short of the true end this time, confirmed by the tool's own "[...truncated, use read_page...]" trailer) — full-content replace off truncated data would have corrupted the live file. CodeMirror's own in-editor find/replace is the safer method for any future targeted mid-file fix; only fall back to full-content replace (via `execCommand('insertText')`) for appends or when the full content has been verified complete.
**Verified live post-fix**: confirmed via `document.querySelector('[class*="group/grid"]')` after dispatching a real `change` event on the year `<select>` (a plain `.value =` assignment without dispatching `change` does NOT trigger the filter's fetch/re-render — needed `select.dispatchEvent(new Event('change', {bubbles:true}))`) that the re-rendered cards use the custom `buildCardHtml` wrapper class (`"group relative flex h-full flex-col gap-4"`), and that a product confirmed to have `imgCount:1` via the API now renders an `<img>` pointing to `media.zid.store` instead of a broken src. The native "X من أصل Y منتج" count text is NOT updated by this filter (it's separate native Zid UI) — don't treat an unchanged count as evidence the filter didn't run.

**Year filter UX fix (v2), DEPLOYED AND VERIFIED LIVE 2026-09-10 — fixed "sudden appearance" + "sometimes needs a refresh" complaints.** User reported the filter was slow to load and sometimes required a manual page refresh after waiting. Root-caused by reading the live script directly (not the editor) and testing in a real browser:
- **Confirmed NOT an SPA-routing issue** — tested directly: clicking a category nav link wipes a `window` test flag, proving this storefront does full page reloads on navigation, not client-side routing. So `DOMContentLoaded` firing once per real page load was never the problem.
- **Confirmed NOT a grid-availability race either** — the product grid (`[class*="group/grid"]`) is already present in the DOM at `readyState: "interactive"`, essentially immediately.
- **Real causes, both UX-level:** (1) the v1 filter `<select>` only got inserted into the DOM *after* `fetchAllProducts()` fully resolved (sequential paginated fetches, ~700-900ms for a 2-page category) — so it always "popped in" abruptly with no loading indicator, which reads as slow/broken even though the underlying fetch wasn't actually hung; (2) v1 had no timeout/retry on the fetch calls at all, so a slow or dropped network request would leave the async chain hung forever with nothing ever rendering until a manual refresh retried it fresh.

Wraps every request in an 8s `AbortController` timeout + one retry, so a stalled call can't leave the UI stuck. Parallelizes the paginated category fetch (first page sequential to learn `pages_count`, remaining pages via `Promise.all`) instead of one page at a time - meaningfully faster on larger categories. Adds a defensive grid-retry-poll (up to 20×150ms) and a `pageshow` handler for bfcache-restored back/forward navigation, as safety nets even though neither was the confirmed root cause - cheap to include, no downside.
- **Negative-case behavior preserved:** for a category with zero year-tagged products (BMW, VW, most of Porsche as of this deploy), the loading placeholder is inserted then immediately removed once the fetch confirms no years exist - a brief flash, never a stuck dead dropdown, never a fabricated year.

**Cross-axis "Category/Model" filter (v3), DEPLOYED AND VERIFIED LIVE 2026-09-10 — adds a second dropdown alongside Year, filtering by whichever axis the current page ISN'T already organized by.** User's idea: on a MODEL page (e.g. "Audi A6") also let the shopper filter by part-type (Lighting, Brakes, Body...); on a PART-TYPE page (e.g. "Porsche Lighting") also let them filter by Model (Cayenne, Panamera...). Both dropdowns apply together (AND).
- **Key enabler, confirmed live before building anything:** every product on this store already carries BOTH a model tag and a part-type tag simultaneously (plus the brand root tag) in the `categories` array returned by `/api/v1/products?categories=X` - e.g. an Audi A6 wishbone product's `categories` are `[1616292 (Audi Parts root), 1616296 (Audi Lighting), 1701831 (Audi A6)]`. This is purely a client-side filter over data that already exists - no new tagging work needed for this feature itself.
- **Implementation:** a hardcoded `CATEGORY_META` map (category id → `{brand, type: 'root'|'model'|'part', en, ar}`) built from the live `ProductCategories.list` data for all 4 brands. On page load, looks up the current category's `type`; if `model`, the cross-dropdown offers that brand's `part`-type categories found among the fetched products' tags (and vice versa for a `part`-type page). Reuses the exact same already-fetched product list as the Year filter (no extra fetch needed) - the cross-filter's option-building and the Year filter's option-building both run in the same `.then()` after one `fetchAllProducts()` call. `applyFilters()` combines both selections (AND) over the product list, replacing the grid; "All"+"All" restores the native grid exactly.

**CONFIRMED PLATFORM CONSTRAINT: `vpic.nhtsa.gov`'s VIN-decode API cannot be called via client-side `fetch()`/XHR from a browser, even though the domain itself is reachable.** Verified three ways: (1) this session's own browser tooling got `TypeError: Failed to fetch` on every call style (normal fetch, `no-cors` fetch, even direct tab navigation to the raw JSON endpoint showed an error page) while other external APIs (`api.github.com`, `jsonplaceholder.typicode.com`) fetched fine from the exact same page - ruling out a general network/CSP block; (2) the store owner's own real phone, on a real Saudi mobile network, got the identical in-page failure ("تعذر الاتصال بخدمة فك التشفير") when submitting a VIN, while a plain URL-bar visit to the NHTSA docs page loaded fine; (3) this matches known bot/WAF protection on `.gov` APIs that blocks programmatic fetch/XHR-style requests while still allowing normal page navigation. **How to apply: never build a feature on this store (or probably any client-side storefront) that does `fetch()` to `vpic.nhtsa.gov` directly - it will silently fail in production regardless of how reachable the domain looks in a browser bar.** The NHTSA "standalone vPIC database" download (linked from their API docs page) is NOT a workaround either - it's a 190MB SQL Server backup (or 69MB PostgreSQL dump) meant to be restored into a real database server, unusable from a static storefront script.

**Real fix shipped (v2): fully local, no external API call at all.** Decodes only what's reliably derivable client-side:

- **Model year (VIN position 10)** via the standard ISO 3779 30-year-cycle letter/digit table, disambiguated by picking the most recent cycle that doesn't exceed the current year (e.g. code "6" → 2006, not 2036, since 2036 hasn't happened yet) - self-correcting as real time passes, needs no manufacturer-specific rule. Verified against the real test VIN `WBANE31086B948101`: NHTSA's own decode (owner checked manually) said BMW **5 Series**, 2006 - this script's local decode correctly gets BMW + 2006 (redirects to the BMW ROOT category, not the 5-Series subcategory - see below for why).

If model-level precision is ever wanted, the real options are (a) a small server-side proxy that calls NHTSA server-to-server (not subject to browser fetch-blocking) - real new infrastructure the store doesn't otherwise have, or (b) hand-researched per-brand VDS tables accepted with explicit accuracy risk.
