Part of [[project_laser_auto_parts]] and [[project_laser_auto_parts_catalog_quality]]. Triggered by owner reporting garbled English typos ("Audiaudi", "Eront Bumpper Suppot", "Radiator Suppot Uper", "Whil Ffender Liner Fornt") visible below Arabic titles and in URLs.

**CONFIRMED LIVE 2026-09-14: Zid does NOT auto-create a permanent redirect when a product's SEO URL slug changes.** Tested directly: changed a product's slug via the dashboard bulk-import "رابط صفحة SEO" field, then fetched the OLD url — got a genuine HTTP 404 (`redirect:'manual'` showed no Location header, no 3xx). This confirms and extends the earlier category-slug finding (2026-09-12, see [[project_laser_auto_parts_catalog_quality]]) to products specifically. **How to apply: any future slug/URL change on this store is a real, permanent dead link for the old URL — there is no platform safety net. Weigh this before renaming any indexed/shared product URL.**

**Storefront URL structure reminder: product pages live at `/products/<slug>`, NOT bare `/<slug>`** — a bare-root fetch 404s even for a perfectly valid, long-established product. Always use the `/products/` prefix when testing/sharing product URLs on this store.

**Root cause of the visible typos: a fixed content-generation TEMPLATE used one "part name" phrase to build `short_description_en`, `description_en`, `product_page_title_en`, `product_page_description_en`, `product_page_url` (slug), and one `keywords` token — all five/six fields copy the SAME phrase.** In an earlier session's title-audit pass, only the main `name_en` field got corrected for many products; the other 5 fields were never regenerated, so they kept the original garbled phrase even after the visible product name looked fine. **Fix method: derive the correct phrase from the already-verified `name_en` (strip the trailing " - Brand Model (years)" suffix), then reconstruct all 5 fields from the same template** (`<phrase> for <brand> <model> <years> — part no. <sku>.` / `<p>High-quality <phrase>, compatible with <brand> <model> vehicles...</p>` + original `<ul>` block preserved verbatim / `<phrase> - <brand> <model> | OEM Part` / `Buy <phrase> compatible with <brand> <model> <years>, part number <sku>. High quality, guaranteed fitment, and fast shipping across Saudi Arabia.` / slugify(`<phrase> <brand> <model> <sku>`)) rather than doing a substring find/replace on the old dirty text — substring replace fails whenever a product's true corrected identity differs from a naive spelling fix (e.g. `Radiator Suppot For` → real identity is `Front Cowling`, not `Radiator Support For`) and also failed on a product that had been PARTIALLY fixed already (short_description clean, SEO title still dirty) since the two fields no longer shared one common dirty substring.
**Side discovery: this template bug also caused silent data truncation** — `product_page_description_en` has some length cap around 155-160 chars, and several longer dirty phrases (`S Line Foglamp Cover Black Right...`) got cut off mid-sentence ("...fast shipping across" with no "Saudi Arabia."). Full template reconstruction with the (usually shorter, correct) phrase fixes this as a side effect.

**Scope found via a fresh export scan (broader token list than the owner's 4 examples — also found "Sapute", "Headlame", "Engin", "Poitalframe", "Foge", "Bosing", "Covrt", "Whill"/"Whil", "Ejngine", "Barake", "Til"): 29 published products affected.** Two false-positive tokens to watch for if re-running a similar scan: `Uper` and `Til` without word-boundaries match inside legitimate words ("Super", "until") — always use `\bToken\b` regex, not a bare substring test.

**Combined in the same bulk-import pass, per owner instruction, with the pre-existing "SKU stray C/T prefix" cleanup** (documented in [[project_laser_auto_parts_catalog_quality]] as blocked/deferred) — 87 more live Audi/Porsche products still had the space-separated `C `/`T ` SKU prefix (the BMW no-space variant was already fixed 2026-09-14 separately). Combined unique set: **101 products** (15 overlap between the two fixes, 72 SKU-only, 14 SEO-only). Zero SKU or URL collisions found before submitting (checked against a fresh full-catalog export). **Bulk import via the dashboard succeeded for all 101 rows in ~15 seconds** (`hermod.zid.sa/v1/jobs/import_products/` job status went running→succeeded, monitored via a `window.fetch` wrapper capturing responses, same technique as documented in [[project_laser_auto_parts_catalog_quality]]).

**Bulk-import dashboard navigation (reconfirmed, exact UI path 2026-09-14): Products page → "⋮" button next to the purple "إنشاء" button (NOT the global "+ إضافة" button top-right, which opens an unrelated quick-add menu) → "استيراد المنتجات" → select "تحديث المنتجات الحالية" radio → "عرض المزيد" to reveal all field checkboxes → check every field you intend to update (checkboxes reset each time the dialog reopens, must re-check every time) → "تحميل" downloads a template pre-shaped to checked fields → fill and "رفع" to upload the file (use the `file_upload` claude-in-chrome tool with a `find`-located file input `ref`, NEVER click the upload button directly — it opens a native OS file picker that automation can't see/interact with) → "استيراد" button to submit (stays disabled until a file is attached).** Template columns matched the export's own column names exactly (`sku`, `new_sku`, `name_en`, `description_en`, `short_description_en`, `product_page_title_en`, `product_page_description_en`, `product_page_url`, `keywords`, etc.) — build the upload file by taking the downloaded template's row0 (category headers) + row1 (field names) verbatim and appending only real data rows.

**SECOND, SEPARATE bug found while verifying the fix live: the "English name below Arabic title" feature customers see is driven by a static custom-JS lookup table (`EN_NAMES`), NOT the live database field.** Documented mechanism (see also [[project_laser_auto_parts_catalog_quality]] item "English-name display on Arabic product pages"): a `var EN_NAMES = {sku: nameEn}` object (~278 entries originally, built 2026-09-11) lives inside an IIFE in the theme's custom JS (dashboard → الثيمات → theme "⋮" → "تعديل JS", theme name "نمو"/Nemo currently), declared at (then) line 741, read at line 748 via `EN_NAMES[sku]` where `sku` is scraped from the visible "SKU ..." text on the page. **This table is a point-in-time snapshot and does NOT auto-update when the real `name_en` field or `sku` changes** — so fixing the 29 typo'd products' real database fields left the customer-visible subtitle still showing the old garbled text, and stripping the "C "/"T " SKU prefix on 87 products broke the table's exact-match lookup entirely for those (their new stripped SKU has no entry, since the table's keys still had the old prefixed SKU) — this would have silently shown NO English line at all for those 87 products if not also fixed.
**Fix applied 2026-09-14: regenerated the WHOLE `EN_NAMES` table from a fresh full-catalog export (overlaid with the 101 just-completed corrections) covering ALL 666 currently-published products** (not just the original 278) — closes the long-standing "coverage gap" noted in the catalog-quality file at the same time.
**Deployment method that actually works for a large (100KB+) full-content JS replacement, since this editor is CodeMirror 6 with no exposed JS API on the DOM (`.CodeMirror` doesn't exist, `.cm-editor`'s node has no reachable view/state reference) and typing char-by-char is impractically slow:** (1) build the new full file content locally in Node, `node --check` it to confirm valid syntax before ever touching the live editor, (2) set the OS clipboard directly from PowerShell (`Get-Content -Raw -Encoding UTF8 <path> | Set-Clipboard`) — bypasses ever passing 100KB+ of text through a tool call, (3) in the browser, click into the editor, `Ctrl+A` then `Ctrl+V` to replace the entire content in one paste, (4) verify via the editor's own built-in search (`Ctrl+F` opens a CodeMirror 6 search panel with `next`/`previous`/`all` buttons — no visible match-count text, but clicking "next" scrolls to a match if one exists, or stays put if none does) — search for a known fixed string to confirm presence, then search for the known-bad old string and confirm "next" does NOT move, (5) only then click "حفظ" (Save), confirmed via a "تم تحديث كود JS بنجاح" toast.
**Splice gotcha hit and fixed: when programmatically replacing one `var X = {...};` statement inside a larger file by string-slicing around an end-marker that includes the OLD closing `};`, you must skip past those 2 characters in the "after" slice AND add your own trailing `;` after the new value** — naively concatenating `before + 'var X = ' + newValue + oldContent.slice(endMarkerIdx)` (where the marker string itself starts with `};`) produces a double-closed `{...}};` and a hard syntax error. Always `node --check` the spliced result before pasting into any live editor.

**UNRESOLVED, found while investigating the EN_NAMES fix — separate, much larger-scope issue, needs owner decision before acting: nearly all BMW products show Arabic text instead of English in the card-subtitle slot (seen on "قد يعجبك أيضاً"/related-product cards), NOT because of EN_NAMES, but because of a genuinely different, NATIVE Zid theme feature that derives that same visual slot's text from the product's own URL SLUG (not from EN_NAMES, not from `name_en`).** Root cause: **every BMW product was created via the `Products.create` API, which — confirmed unfixable via any parameter, see [[project_laser_auto_parts_catalog_quality]] — always auto-generates the slug from the ARABIC name, never English.** Since the slug is 100% Arabic Unicode text for these products, the native theme feature that reformats the slug into a card subtitle just shows Arabic. Confirmed live via the public API: sampled BMW products' `slug` field is fully Arabic (e.g. `فلتر-زيت-المحرك-لسيارات-bmw-...`). **Scope is large — likely 700+ products** (the 374-item 2026-09-12/13 gap-fill batch plus however many of the ~485 pre-existing/legacy BMW products were also API-created) — this is the SAME redirect-less slug-change mechanism already proven above, so fixing it means generating ~700+ new English slugs via the same bulk-import method and permanently 404-ing that many old (Arabic, likely low-SEO-value) URLs. **Owner decision 2026-09-14: SKIP this fix.** Assessed as low priority — the broken text is only a secondary gray subtitle line on related-product/card grids (not the primary product name, which is Arabic and already correct everywhere), while the store's customer base is Arabic-first. Fixing it would 404 ~700+ live URLs permanently (no redirect, per the confirmed finding above) for a payoff most visitors won't consciously notice. Contrast with the 29-product typo fix done the same session, which was in primary SEO titles/meta descriptions/visible short-descriptions — real indexed, read content. **Not planned — do not re-propose this without new information changing the cost/benefit** (e.g. if the owner later reports actual customer confusion tied to this specific subtitle).
