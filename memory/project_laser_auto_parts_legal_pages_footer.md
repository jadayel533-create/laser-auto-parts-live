Part of [[project_laser_auto_parts]]. Covers a same-session arc: owner said "سياسة الاسترجاع doesn't show up anywhere" → found the content existed but was unlinked → fixed via footer, not header nav (owner corrected the first attempt).

**Root cause:** the store has TWO separate systems for legal-style pages on this platform, easy to confuse:
1. **Settings → الصفحات القانونية (Legal Pages)** — a dedicated settings area (`/settings/legal-pages`) with fixed slots (Privacy/Terms/Return-Exchange/Complaints). Checked directly: this store's "سياسة الاستبدال والإرجاع" slot here is completely EMPTY (blank name + blank content) — never used.
2. **المتجر الإلكتروني → الصفحات (custom Pages app)** — a separate, generic custom-pages list (`/channels/online-store/pages`). This is where the owner's real content actually lives: نبذة عن المتجر, سياسة الخصوصية, سياسة الاستبدال والاسترجاع, سياسة الشكاوى والاقتراحات, الشروط والأحكام — all filled in with real bilingual content, but a Page created here is NOT automatically linked into any menu/footer. That's the entire "doesn't show up anywhere" mystery: real content, zero linkage.
**How to apply:** if a future "policy page missing" report comes in, check the Pages app list FIRST (dashboard → المتجر الإلكتروني → الصفحات) before assuming content needs to be (re)written — it's very likely already there, just unlinked.
**Recurrence 2026-09-13:** a competitor-benchmark research fork flagged our policy pages as "disabled/empty in store settings," which fed a wrong recommendation into a report. It had checked the dedicated Settings → الصفحات القانونية (Legal Pages) slots (confirmed empty, per the root-cause note above) without knowing the REAL content lives in the separate Pages app and was already fixed/linked via the footer. Live re-check confirmed all 4 pages (`/pages/سياسة-الخصوصية`, `/pages/سياسة-الاستبدال-والاسترجاع`, `/pages/الشروط-والأحكام`, `/pages/سياسة-الشكاوى-والاقتراحات`) resolve correctly and are linked in the footer. **How to apply, reinforced: any fresh agent/fork auditing this store's "trust signals" or legal/policy content must be told explicitly to check the live footer + Pages app, not just a `legal_pages`-style settings field — the settings field alone will always read as empty/broken on this store even though the real content is fine.**

**Page URL quirk:** the "الصفحات" edit screen's own "رابط التصنيف" hint shows a `/blogs/<slug>` URL and literally warns that for the currently-active theme/template you must swap `blogs`→`pages` in the URL for it to resolve. Confirmed live: `/blogs/...` 404s, `/pages/<url-encoded-arabic-slug>` is the real working URL. Don't trust the dashboard's own displayed URL for this theme without checking.

**Fix, attempt 1 (superseded by owner correction) — top nav "Custom Elements":** Dashboard → المتجر الإلكتروني → القائمة الرئيسية (main menu) has an "العناصر المخصصة" (Custom Elements) toggle + add-link flow supporting link-type "صفحة إضافية" (Additional Page) pointing at one of the Pages-app entries. Tried this — the "page"-type link rendered live but resolved to a broken `href="/pages/None"` (a real, confirmed Zid bug: the page-type custom nav item doesn't resolve the selected page's real slug). Switched to link-type "رابط خارجي" (External Link) with the page's real full URL typed in manually — that one worked correctly (verified end-to-end, real navigation to the real page). **Note the live storefront nav is cached with a real propagation lag (multiple minutes, not instant)** — a change can appear to "not have taken" and then correct itself, or vice versa; always re-check with a fresh cache-busted load before concluding a nav edit failed or succeeded.
**Owner then said this was wrong placement anyway** ("you placed it in the header bar instead of the categories, we want them down in the footer, with the contact us") — deleted the header Custom Elements entry entirely (dashboard confirms empty list). **How to apply: don't use the dashboard's header "Custom Elements" feature for policy-page links on this store going forward — the owner wants these in the footer, and the feature has a live confirmed bug on the "page" link-type anyway.**

**Fix, final (deployed via custom-JS, matches this store's established injection pattern) — footer "روابط تهمك" (Useful Links) block + Contact-Us reposition, DEPLOYED AND VERIFIED LIVE 2026-09-12/13, both desktop and real mobile viewport (Playwright 390px).**
- Footer DOM shape: `footer > .theme-container > .grid` (2 columns, `grid-cols-1 md:grid-cols-[repeat(auto-fit,minmax(250px,1fr))]`). Column 1 = logo images + 3 empty (unused) description `<p>` tags + "تابعنا" (Follow Us) heading + social-icon row. Column 2 = "تواصل معنا" (Contact Us) heading + email/phone list.
- **New IIFE #1** finds the "تواصل معنا" `<h3>`'s parent block in column 2, builds a matching-style `<div class="legal-links-block">` with an `<h3>روابط تهمك</h3>` + `<ul>` of the 4 real page links (`/pages/سياسة-الخصوصية`, `/pages/سياسة-الاستبدال-والاسترجاع`, `/pages/الشروط-والأحكام`, `/pages/سياسة-الشكاوى-والاقتراحات` — all pre-verified 200 via same-origin fetch before hardcoding), and inserts it into column 2 right before the Contact-Us block. Bounded retry-poll (20×150ms), matching the established pattern elsewhere in this file's custom-scripts.js.
- **New IIFE #2** (added right after owner's footer-placement correction) moves the Contact-Us `<div>` (found the same way, by its own h3 text) out of column 2 and into column 1, inserted right before the "تابعنا" heading — so column 1 reads Logo → Contact Us → Follow Us, and column 2 is now just the Useful-Links block alone. Uses a `dataset.reordered` guard so it only runs once even if it fires multiple times off the retry-poll.
- **Link style reused from the site's own existing contact-info link** (`class="text-foreground text-sm"`) rather than inventing new classes — confirmed via live DOM inspection of the real email link before writing the new links, so it automatically follows the site's dark/light theme tokens with no extra CSS needed.
- Both blocks deployed via the same direct-`view.dispatch()`-append method documented in [[project_laser_auto_parts_dark_mode]] (read `.cm-content`'s `cmView.view`, confirm doc length matches a fresh live-fetch backup before appending, append the new IIFE text, confirm doc length grew by exactly the inserted string's length, verify the tail, THEN click حفظ). No full-content reconstruction needed for either edit.
- **Verified live end-to-end, not just via the injected test copy:** fresh cache-busted page loads (both as the owner's authenticated Chrome tab and via Playwright's independent browser) show the footer correctly ordered on desktop; Playwright at 390×844 shows it stacking cleanly Logo → Contact Us → Follow Us → Useful Links → copyright/payment row, with the return-policy link's `href` resolving to the real URL-encoded page path.
