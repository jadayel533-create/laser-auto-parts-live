**Editor pitfall discovered and worked around — IMPORTANT for any future edit to these boxes:** both custom-code editors are CodeMirror 6 with an aggressive auto-close-bracket/quote feature that does NOT reliably "type over" a manually-typed matching closer when the content typed between the opener and closer spans multiple lines (which is always true for real code). Typing the addition in one large `type` call froze the tab outright (had to be manually refreshed, twice); typing in small chunks avoided freezing but left stray orphaned auto-inserted closing characters scattered through the document (7 stray `}` at the very end for the ~90-line CSS addition; for the ~150-line JS addition, one stray `}` mid-document plus ~180 stray characters at the end, none of it visible in the editor's own display — this store's known display-truncation bug hid the corruption completely even under close visual inspection). **How this was actually fixed:** the editor's `.cm-content` DOM node exposes a `cmView.view` property (a live CodeMirror `EditorView` instance) — `view.state.doc.toString()` reads the true current buffer content directly (bypassing the display bug entirely), and `view.dispatch({changes:{from, to, insert}})` writes to it directly (bypassing the keystroke-simulation/auto-close pipeline entirely, so it never re-triggers the bug). For the JS box specifically, once corruption was found, the cleanest fix was locating the addition's start offset via `doc.toString().indexOf(anchorText)` and replacing everything from there to the end of the document in one `dispatch` call with the exact known-good source (verified with `node -c` beforehand) — far more reliable than trying to hand-patch each stray character. CSS was small enough to hand-patch via precise backspace-count-and-recheck instead. **For any future edit to either box: prefer the direct `view.dispatch()` approach over simulated typing from the start, or at minimum verify the FULL saved content afterward via a live fetch + `new Function(text)` syntax check (for JS) before trusting anything typed into either editor.**

**Follow-up fix, same session 2026-09-12 — header logo recolored white-on-dark, done via direct CodeMirror manipulation (not simulated typing).** Owner reported the header logo's wordmark text stayed black in dark mode. The logo (`alt="Laser Auto parts"`, same alt text regardless of AR/EN locale) is a single flattened PNG — no separate text/icon layers — combining the black "LASER AUTO PARTS" text with a red car-outline icon. Confirmed via a full pixel-color histogram of the live image that this catalog's logo only ever uses **pure black** (the text) and **pure red, G=B=0** (the car icon, with anti-aliased R-channel-only edge blends) — no other hues — so a simple "recolor near-black pixels to white, leave everything else untouched" pass is provably safe: any pixel with R<40 AND G<40 AND B<40 → white; everything else left byte-for-byte unchanged (re-verified via histogram after the recolor: white-pixel count matches the original black-pixel count almost exactly, every red-pixel-group count is unchanged to the pixel).
- **CORS note:** `media.zid.store`'s CORS policy allowed canvas pixel access (`img.crossOrigin='anonymous'` + `getImageData`) when the fetch originated from `laserautoparts.com` (the storefront's own origin) but silently failed when the exact same request was made from `dashboard.zid.sa` — needed to do the actual recolor computation in a storefront tab, not the dashboard tab where the code editor lives.
- **Cross-tab transfer of the resulting ~13KB base64 PNG turned out to be the hard part, not the image processing.** `navigator.clipboard.writeText()` and `document.execCommand('copy')` both failed ("Document is not focused" / silent `false`) when triggered via this automation path. What worked: trigger a normal browser file download of the data URL (`<a download>` + `.click()`) from the storefront tab, landing the PNG in the user's real Downloads folder, then read+base64-encode it locally via Node and re-embed it as a literal string directly into a `view.dispatch()` call in the dashboard tab's CodeMirror instance (same direct-manipulation technique documented above) — no clipboard, no focus requirements, fully reliable.
- **New editor-input limit discovered: a single `javascript_exec` call embedding roughly >12,000 characters of literal string content gets silently truncated** (not blocked, not erroneous — the script executes fine, just with truncated string data, so it reads as if it worked and self-reports a length that's actually short). Caught this via `naturalWidth === 0` on a `complete === true` image (classic "decode failed on truncated/corrupt data" signature), not via any explicit error. **Fix: split large string payloads into ≤4000-char chunks and append each via a separate small `dispatch()` call**, tracking the insertion offset numerically across calls rather than re-searching text each time (search-based re-location gets awkward once you don't know how much of a giant string actually landed). Confirmed working reliably at 4000-char chunk size for a 13,320-char payload (4 calls). This 12K-ish ceiling is a distinct, separate limit from the earlier-documented auto-bracket-closing corruption bug (that one happens on simulated typing; this one is a raw input-size cap on the exec call itself, and doesn't care whether the content is code or a big literal string).
- **Also reconfirmed the tool's OUTPUT-side content filter ("[BLOCKED: Cookie/query string data]" / "[BLOCKED: Base64 encoded data]") triggers on returning long base64-ish or URL-ish strings from `javascript_exec`** back into the conversation, even for entirely innocuous data (this store's own logo PNG, a public CDN image URL) — a `data:image/...;base64,` PREFIX seems to make the filter treat the string as a recognized/safe image and let short slices through, but a bare base64 fragment without that prefix, or anything that looks like a long opaque token, gets blocked regardless of actual sensitivity. **Workaround used throughout: never round-trip large data through the return value at all — do the read, transform, AND write all inside the page context via direct DOM/editor manipulation, only returning small booleans/numbers/lengths to the conversation for verification.** This is the same principle as the CodeMirror-`view.dispatch()` technique above, just generalized: prefer "do everything in-page, report a summary" over "fetch data out, process it, send it back in" whenever a payload is more than a few hundred characters.
- **Final result, live-verified 2026-09-12 (real deployed code, not a temp injection):** clicking the theme toggle swaps the header logo between the original (light mode) and the white-text version (dark mode) instantly, on every page template tested (home, BMW category), confirmed both by pixel-color histogram (white-pixel count ≈ original black-pixel count, every red-pixel-group count unchanged) and by `naturalWidth`/`isDataUrl` checks after clicking. The recolor logic lives in its own independent IIFE block (search `Dark-mode logo recolor` in custom-scripts.js) that watches `<html>`'s class via `MutationObserver` rather than calling into the main toggle script's functions directly — so it keeps working even if that script gets edited again later without this block being touched.

**Design of the toggle mechanism (implemented in the JS addition file):**
- Two explicit override classes on `<html>`: `.theme-dark` / `.theme-light`, driven by a `localStorage` key `laser-theme` ("dark" | "light" | absent).
- When neither class is present (no explicit choice made yet), a `@media (prefers-color-scheme: dark)` block in the CSS makes the site follow the visitor's OS-level preference automatically — this path has **zero flash** since it's pure CSS resolved before first paint, no JS dependency.
- The **only** scenario with a possible brief flash: a returning visitor whose explicit stored choice differs from their current OS preference (e.g. explicitly chose dark while their OS is set to light) — the page will briefly show the OS-matching look until the end-of-body script runs and swaps the class. This is a deliberate, documented tradeoff given finding #4 above (no head-script injection point found) — not a bug to chase further unless a future session finds an actual head-injection slot in the dashboard UI.
- Toggle button injected in two places via stable-selector anchoring (not fragile CSS classes that could get regenerated): next to the desktop region/language-switcher button in the header's icon `<ul>` (found via `button[onclick="zidOpenRegionSettingDialog()"]`), and next to its counterpart inside the mobile drawer (found via the drawer-closing variant of the same onclick string). Both use a bounded retry-poll (20x150ms) matching the existing pattern already used elsewhere in this file (e.g. the English-name-injection feature), in case of any hydration timing quirk — though testing found the buttons are present in the initial DOM (not lazily mounted), so this is a defensive-only safeguard.
- Sun/moon SVG icon swap on click, matching the existing header icon button style/sizing exactly (`flex size-10 items-center justify-center`, `class="text-foreground"` on the svg) for visual consistency with the cart/account/search icons already there.
